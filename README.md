# AnalyzeFiles

Сервис скачивает каталог текстовых файлов через внешнее API и считает статистику
встречаемости цифр (0-9) - общую и по каждому файлу. Простой веб-интерфейс из двух
страниц: скачивание и список скачанного с расчётами.

## Стек

- FastAPI + `httpx.AsyncClient` для внешнего API.
- SQLite (метаданные и кеш статистики), содержимое файлов - на диске в `data/files/`.
- Jinja2-шаблоны + vanilla JS, без сборки.

## Запуск

Нужен [uv](https://docs.astral.sh/uv/) - установить можно через `pip install uv`,
`pipx install uv` или официальным установщиком со страницы uv. После старта открыть
`http://127.0.0.1:8000/` - страница скачивания, `/files` - список и расчёты.

Через make (короткие обёртки над uv):

```bash
make install    # uv sync - установить зависимости
make run        # запустить сервер с автоперезагрузкой
make check      # ruff + mypy + pytest
make test       # только тесты
```

Через uv напрямую (если make недоступен, например на Windows без GNU Make):

```bash
uv sync
uv run uvicorn app.main:app --reload
uv run pytest
```

Вручную, в активированном виртуальном окружении:

```bash
uv sync
. .venv/bin/activate        # Windows: .venv\Scripts\activate
uvicorn app.main:app --reload
```

Порт по умолчанию 8000; сменить - флагом `uvicorn ... --port 8001`.

## Переменные окружения

Задаются в `.env` или окружении (см. `app/config.py`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `EXTERNAL_BASE_URL` | адрес внешнего API | Базовый URL источника файлов |
| `PRECOMPUTE_ON_DOWNLOAD` | `true` | Считать статистику сразу при скачивании |
| `DATA_DIR` | `data` | Каталог для файлов и SQLite |

## Работа с внешним API

Скачивание идёт фоновой задачей с состоянием (получено / скачано / не скачались),
прогресс отдаётся на фронт через polling статуса. Батчим имена по мере получения,
скачиваем не больше 3 за запрос, отмечаем скачанным только после записи на диск.
Подводные камни API и решения по ним - в разделе "Каверзные случаи и решения" ниже.

## Режимы расчёта

ТЗ не уточняет, когда считать статистику, поэтому выбор сделан опциональным.

- **`PRECOMPUTE_ON_DOWNLOAD=true` (по умолчанию)** - 10 счётчиков считаются один раз в
  момент скачивания (содержимое уже в памяти после распаковки) и кладутся в SQLite.
  Кнопка "Произвести расчёты" тогда не читает файлы вовсе - результат мгновенный на
  любом объёме. Это выбранный основной подход.
- **Чекбокс "Пересчитать заново из файлов"** на странице расчётов (`recalculate`) -
  режим "в лоб": читает и парсит выбранные файлы прямо по нажатию, игнорируя кеш, и
  обновляет его. Полезно, если файлы на диске меняли вручную и кеш устарел.
- Если `PRECOMPUTE_ON_DOWNLOAD=false` (или для файлов, скачанных до включения кеша) -
  первый расчёт читает файлы, считает и кеширует лениво, последующие мгновенны.

## Производительность

Замеры на реальных данных: 1234 файла по 500 байт (~600 КБ).

Подсчёт цифр по всему каталогу:

| Метод | Время |
|---|---|
| чтение 1234 файлов с диска | ~160 мс (доминирует) |
| char-loop (посимвольно) | 37 мс |
| `str.count` (используется) | 8 мс |
| `collections.Counter` | 18 мс |
| чтение потоками x4/x8/x16/x32 | 150-175 мс (не ускоряет) |

Расчёт через `POST /api/files/calculate` по всем файлам:

| Сценарий | Время |
|---|---|
| первый расчёт (чтение с диска + кеширование) | ~0.27 с |
| из кеша | ~0.016 с (~16x) |
| `recalculate=true` (перечитать всё) | ~0.23 с |

Узкое место - не вычисление (один проход `str.count` это единицы миллисекунд), а
оверхед открытия множества мелких файлов. Поэтому статистика кешируется в SQLite и
файлы при повторном расчёте не читаются.

## Каверзные случаи и решения

К задаче я подошёл как к боевой, а не учебной: продумал не только happy-path, но и
краевые сценарии, которые в реальной эксплуатации действительно случаются - сетевые
сбои, частичная недоступность данных, гонки при перезапуске, некорректный ввод. В
финтехе и распределённых системах цена такой ошибки высока (потерянные или задвоенные
данные, зависшие процессы), поэтому по каждому подводному камню заложено явное и
предсказуемое поведение:

- **Общее число файлов неизвестно.** Признак завершения - `/api/files/names` перестал
  отдавать новые имена. Никакого хардкода количества.
- **Лимит частоты (429) и бан (403 на 30 минут, по IP).** Клиент адаптивный: пол паузы
  между запросами + экспоненциальный backoff с джиттером, честный `Retry-After`,
  плавное ускорение на успехах. Длительность бана из 403 не превращается в темп. На
  практике сводит 403 к нулю.
- **Порядок download -> запись на диск -> mark.** Файл отмечаем скачанным только после
  реальной записи. Иначе при сбое между шагами он исчез бы из выдачи имён, но не оказался
  на диске - потеря навсегда.
- **Одинаковые имена и перезапуск посреди процесса.** В БД `INSERT OR REPLACE`, на диске
  перезапись - операция идемпотентна. Прогресс восстанавливается из SQLite и файловой
  системы, а не только из памяти.
- **Файл не скачивается (404 / битый ZIP).** Не роняем весь процесс: проблемный чанк
  перекачиваем по одному, виновника пропускаем (не отмечая на сервере, чтобы не соврать),
  остальной каталог докачивается. Пропущенные видны в счётчике "Не скачались". Цикл всё
  равно завершается: провальные имена не возвращаются в обработку повторно.
- **Zip-slip (путь в имени внутри архива).** Берём только `basename`, запись вне целевого
  каталога невозможна.
- **Не-цифры или длина != 500 в содержимом.** Цифры считаются как обычно, но фиксируются
  число не-цифровых символов и длина; такие файлы попадают в блок "Аномалии". Расчёт не
  падает, данные не теряются.
- **Пропавший или нечитаемый файл на этапе расчёта.** Не роняет весь расчёт - файл
  попадает в список "Не удалось прочитать", остальные считаются как обычно.
- **Большие выборки имён.** Запрос `IN (...)` режется на куски под лимит параметров
  SQLite.
- **Идентификация.** Свой `X-Candidate-Id`, не полагаемся на IP хоста.
